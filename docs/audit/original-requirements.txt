EnglishLearningApp v1.0Codex 完整开发任务
高考英语自适应学习系统 · Android 重构升级规格
请直接在当前 EnglishLearningApp Android 项目基础上进行完整的 v1.0 重构升级。这不是概念设计、UI 原型或仅输出建议的任务，而是需要检查现有代码、理解当前架构、尽量复用已有可靠代码与资源，并最终交付可实际运行、可通过 GitHub Actions 构建 APK 的正式版本。
一、总体原则
不要新建一个与现有项目无关的 App；在当前仓库和现有项目上升级。
核心学习系统必须在无 AI、无网络时仍可正常使用。AI 是增强层，不是硬依赖。
AI 功能仍遵循“用户手动触发”原则，禁止后台偷偷调用 API。
优先保证 Android 手机上的速度、稳定性、低点击延迟和简洁交互。
不要为了功能数量牺牲学习路径清晰度。首页必须让用户一眼知道今天该做什么。
已有词库、音标、音频/音频映射等可靠资源尽量复用，不要无意义重做。
二、产品目标与核心学习闭环
将当前 App 从“英语学习功能集合”重构为：面向高三学生的高考英语自适应学习系统。
1. 本地算法生成今日任务
2. 新词学习
3. 到期词汇复习
4. 随机抽查纠偏
5. 高考阅读训练
6. 必要时插入语法弱项专项
7. 今日综合小测
8. 本地算法更新掌握度、弱项和次日计划
9. 用户可手动触发 AI 分析/解析/预生成内容
三、首页与“今日学习”
v1.0 首页以“今日学习”为唯一主入口。其他词库、错词、统计、AI、设置等退到二级页面，不要让用户每天思考应该点哪个模式。
首页建议展示：
今日预计学习时长
今日新词数量
到期复习词数量
阅读任务
是否存在语法弱项专项
综合小测
当前完成进度
“开始今日学习”主按钮
四、动态每日学习量
默认每天约 20 个新词，但由本地算法根据近期学习情况动态调整，建议范围 15～25 个。复习优先级高于盲目增加新词。
计算时至少考虑：
最近数日新词掌握率
到期复习积压量
随机抽查正确率
拼写正确率
语境题正确率
综合小测成绩
近期学习完成率和可用学习时长
算法应可解释、可测试、参数集中管理。不要把“明天学多少词”的决定交给大模型。
五、词汇学习页：分层显示 + 主动回忆
每个单词建议按以下交互：
首先只显示大字号单词、音标和发音按钮。
进入单词时自动播放美式发音两遍；用户可点击重复播放。
先要求用户在脑中主动回忆，不立即暴露中文答案。
点击“显示释义”后再展开核心义、简短高考语境例句、常见搭配、必要的词形变化。
用户选择“不认识 / 模糊 / 认识”。
现有音标不要无意义重做；已有可靠音频和映射应优先复用。音频应尽可能离线可用。
六、随机抽查纠偏
不能完全相信用户的自评。系统应随机抽查部分被标记为“认识/模糊”的词，通过中英选择、语境选义、拼写等方式校准真实掌握度。
例如用户刚将 maintain 标记为“认识”，随后抽查却选错，则显著降低该词掌握度并提高近期复习优先级。
七、自适应复习算法
实现本地自适应间隔复习引擎。不要只写固定的 1/3/7/14 天 if-else。
掌握度和下一次复习时间至少综合：
认识 / 模糊 / 不认识自评
随机抽查结果
拼写结果
语境选词结果
历史遗忘次数
连续正确次数
最近正确率
距上次学习时间
不同语境下是否仍能正确识别
连续多次在不同形式测试中正确的词才逐渐拉长复习间隔；错误后应缩短间隔并提高权重。
八、高考诊断阅读
阅读模块不是普通“文章 + 答案”，而是诊断型训练。每篇文章应记录题型、正确率、耗时、生词和错误原因。
主旨题
细节题
推断题
词义猜测题
指代题
后续可扩展七选五等题型
阅读过程中允许查看词义并加入生词/重点词记录。结束后统计本篇生词数量以及真正影响理解的词。
跨多篇阅读统计题型表现，例如最近 7 篇推断题正确率最低，从而形成明确弱项。
九、综合小测
每日学习结束设置约 15 题、5～10 分钟的综合小测。建议结构：

综合小测结果必须反馈到本地学习算法。例如当日掌握较差时，次日减少新词、增加复习，而不是固定每天 20 个。
十、语法：诊断驱动弱项专项
不要做一本庞大的电子语法书。通过每日小测、阅读及语法题持续记录错误，按知识点计算薄弱程度。
当某知识点明显薄弱时，自动加入次日“弱项专项”，流程建议：
超短知识卡
典型例题
3～5 道针对题
错题解释
仍不理解时提供“让 AI 给我讲明白”手动按钮
十一、三种学习强度
主线明确，但允许用户临时调整当天学习量：
快速 15 分钟：复习优先 + 少量新词 + 微型测试。
标准 40～45 分钟：完整今日学习流程。
强化 60 分钟：完整流程 + 弱项专项/额外训练。
自定义：允许用户自行调整。
缩短学习时间时优先减少新内容，不应优先砍掉已经到期的核心复习。不要使用断签归零等制造压力的机制。
十二、AI 架构：B+ 本地算法调度 + AI 增强 + 缓存
中转站成本较低，因此 AI 可以参与更多有价值的任务，但核心原则是：本地算法负责确定性工作，AI 负责需要语言理解/生成的增强工作，并尽可能提前生成后缓存。
AI 可用于：
阅读题详细解析与错误原因解释
长难句结构拆解
单词当前语境义解释
高考语境例句/易混辨析补充
根据真实弱项生成针对性练习
本地题库不足时补充小测题
根据本地统计数据生成周学习分析与建议
十三、统一 AI 调度器
不要让每个页面各写一套 API 请求。建立统一 AI Service / AI Task Scheduler，所有 AI 功能通过统一层调用，便于模型切换、错误处理、费用统计和缓存。
调度逻辑示意：
本地算法先分析当前任务和已有缓存。
判断该任务是否真的需要 AI。
不需要 AI：完全本地执行。
需要 AI：加入待生成队列。
用户手动触发“准备明日内容”或对应 AI 按钮后才真正请求。
返回内容进行结构化校验后写入本地缓存。
学习时优先读取缓存，避免重复请求。
十四、AI 预生成与缓存
实现“准备明日内容”功能。用户完成当天学习后，本地先计算明日计划，检查明日可能需要的 AI 内容，用户手动点击后批量生成并保存。第二天学习时直接读取，不应每点一次就等待几十秒。
缓存必须带内容类型、输入摘要/哈希、模型、生成时间、版本等信息，避免重复生成；过期或输入变化时再失效。AI 返回 JSON 时必须进行健壮解析、字段校验和失败降级。

统一记录每一次 AI 调用：

价格配置应可编辑；如果中转站返回 usage 分项则优先使用真实数据，不要伪造。
十六、诊断型统计页
统计页的目的不是堆图表，而是回答：我现在差在哪里？接下来应该练什么？
词汇：稳定掌握、学习中、高频遗忘、拼写正确率等。
阅读：总篇数/题数、各题型正确率、耗时趋势、生词影响。
语法：各知识点正确率和弱项。
学习：平均时长、计划完成率、快速/标准/强化模式使用情况。
自动给出当前 1～3 个最高优先级弱项。
只保留真正有意义的少量图表。另提供“AI 分析本周表现”按钮：先由本地生成结构化统计，再交给 AI 解读。
十七、数据迁移与备份
采用“核心数据迁移”，而不是全部清空或强行保留所有历史垃圾数据。
尽量保留：
现有词库
音标
已有音频/音频映射
能够可靠转换的单词学习状态和错词数据
API / 中转站配置
模型与价格配置
可靠的 Token / 费用历史
用户自定义设置
升级数据库前必须创建可恢复的本地备份。迁移失败不得直接破坏旧数据。废弃页面状态、无意义旧流程数据无需背历史包袱。
十八、UI / UX 要求
整体保持简洁、现代、接近 ChatGPT 式清爽界面。
保留/完善蓝色主题选择。
重点优化此前存在的全局点击延迟问题。
底部导航只能有一层，不允许出现重复两层导航。
页面切换使用轻量、快速的过渡，不要花哨动画。
重要按钮触控区域足够大，适配 Android 手机单手操作。
学习页减少无意义跳转，尽量在 App 内完成，不要频繁跳网页。
加载 AI 时不得阻塞整个界面；允许取消，失败后可重试。
十九、稳定性与离线能力
词汇学习、复习算法、学习计划、统计、小测等核心能力必须离线可用。
无网络或 API 故障时给出明确提示，但不能导致核心学习流程不可用。
AI 内容有缓存时离线直接使用缓存。
数据库操作、音频加载和大列表不得阻塞主线程。
处理 App 重启、异常退出后的学习进度恢复。
二十、开发执行要求
首先审查当前仓库结构、技术栈、数据库、已有页面、词库、音频、API 层和 GitHub Actions，不要凭空假设。
在开始大规模修改前，建立可回滚点/分支并保护现有可运行版本。
能复用的可靠代码复用；明显造成延迟、重复导航或架构混乱的旧代码可以重构。
优先完成数据模型、学习算法和核心学习闭环，再做 AI 增强和视觉打磨。
关键算法写单元测试：掌握度、复习间隔、动态新词量、弱项识别、费用计算等。
对数据库迁移编写迁移测试，避免升级后数据损坏。
构建 Debug/Release，修复编译错误和明显运行时问题。
检查 GitHub Actions，确保最终可以正常构建 APK。
二十一、完成标准
任务完成不能只以“代码已写”为标准。至少满足：
App 可以正常构建和启动。
今日学习主流程从开始到结束完整可走通。
动态学习量与自适应复习算法实际生效。
随机抽查能纠正虚假的“认识”自评。
阅读可以按题型形成诊断数据。
语法弱项能够触发专项训练。
综合小测结果能够影响后续计划。
AI 完全关闭时核心功能仍正常。
AI 统一调度、手动触发、缓存、Token 与费用统计正常。
旧版核心数据可以安全迁移，失败有保护。
明显点击延迟、重复底部导航等旧体验问题得到解决。
GitHub Actions 能构建 APK。
二十二、最终交付
完成后请直接提交实际代码修改，并给出简洁的完成报告，包括：主要改动、架构变化、数据库迁移情况、AI 调度与缓存实现、测试/构建结果、APK 构建方式、仍存在的已知问题。
不要只返回计划、伪代码、截图或 UI 原型。遇到现有项目结构与本规格冲突时，以“保持现有数据安全、核心学习闭环可用、Android 实际体验稳定”为最高优先级自行做合理工程决策。
